## 二、项目一：基于 STM32 的两轮平衡小车控制系统（2026.02 - 2026.04）

**技术关键词：** C、STM32、六轴姿态传感器、双路编码器、串级 PID、PWM 电机控制、闭环控制。

### 项目介绍

这个项目的目标是让两轮小车实时保持直立，并完成定速巡航、转向和基本运动控制。系统以 STM32 为主控，采集六轴姿态传感器和左右轮编码器数据，经过姿态估计、速度计算和串级 PID 后，输出左右电机 PWM 控制量。

我负责六轴姿态传感器数据采集和车体倾角解算、双路编码器测速和反馈、姿态环与速度环组成的串级 PID、左右轮 PWM 合成输出，以及平衡、定速巡航和转向调试。简历中提到的“优化响应速度和运行稳定性”，面试时要结合真实的调参过程和测试现象说明。

### 系统数据流

固定控制周期内依次完成：读取加速度和角速度；姿态融合得到俯仰角和角速度；读取左右编码器增量并计算轮速；速度环生成姿态修正量；姿态环生成平衡输出；将转向量叠加到左右轮，限幅后更新 PWM。可概括为：左右轮输出 = 平衡控制量 + 速度修正量 ± 转向控制量。实际工程还要处理传感器异常、编码器溢出、PWM 限幅和倒地保护。

### 为什么使用串级 PID？

内环是快速姿态环，负责纠正倾角、防止小车倒下；外环是较慢的速度环，负责前进、后退和定速巡航。把两个时间尺度不同的目标分开后，姿态稳定和速度控制不会相互争夺同一个输出，调参和定位也更清晰。内环频率应高于外环，但具体数值要按实际控制周期测量，不能凭空填写。

### 加速度计、陀螺仪和姿态融合

加速度计静止时可利用重力估计倾角，但运动和振动会干扰它；陀螺仪短期响应快，但积分会因零偏漂移。因此使用互补滤波或卡尔曼滤波：高频变化更多参考陀螺仪，低频趋势用加速度计校正。先做零偏校准和坐标轴方向确认，再将融合角度送入姿态环。

### 编码器测速和跑偏处理

在固定采样周期内读取左右编码器增量，结合每圈脉冲数、减速比和轮径换算轮速。左右轮增量平均值用于车体速度，差值用于转向和左右补偿。需要处理计数器溢出、正反转方向、采样周期抖动和线缆噪声。跑偏时先检查左右电机和编码器方向，再做软件补偿，不能只改 PID。

### 抖动或突然倒下如何排查？

先检查重心、轮胎、支架、电机供电和传感器固定；再记录原始角度、角速度、编码器数据、控制周期和 PWM 波形。高频抖动通常检查比例过大、微分噪声和滤波；慢慢跑偏检查左右电机差异、编码器方向和零点；突然倒下检查控制周期丢失、传感器异常、积分饱和和输出限幅。

### 如何保证实时性？

定时器提供稳定节拍，中断只做采样、计数、置标志和轻量计算；OLED、日志和非关键通信放到低优先级任务。控制计算必须在周期内完成，否则会增加相位延迟。如果超时，先减少重复计算和非关键刷新，再考虑拆分任务。面试时需要补充实际主控型号、传感器型号、控制周期和滤波方法。

## 三、项目二：高性能 HTTP 服务器（2026.05 - 2026.06）

**技术关键词：** C++、线程池、epoll、LRU、DJB2、双向链表、哈希表。

### 项目介绍

这是一个 Linux 下的高性能静态 HTTP 服务器。它使用 epoll 做 IO 多路复用，使用非阻塞 socket 管理客户端连接，再用线程池异步处理 HTTP 请求和静态资源响应，支持图片、视频等静态资源。

我主要完成：基于 epoll 实现事件驱动 IO；实现 HTTP/1.1 请求解析，支持 GET、标准状态码和静态资源请求；设计线程池和任务队列，避免 IO 线程被文件处理阻塞；实现文件读取、类型识别和数据返回，并针对大文件设计缓冲区。简历列出的 LRU、DJB2、双向链表和哈希表，应说明它们在缓存或索引中的真实接入位置；若只是模块实验，要明确边界。

### epoll、ET 和一次 GET 请求

select/poll 需要反复遍历 fd 集合；epoll 返回就绪事件，更适合大量连接。非阻塞 socket 在 ET 模式下收到可读事件后必须循环 recv，直到 EAGAIN/EWOULDBLOCK。请求流程是：accept 新连接并加入 epoll；连接可读时把数据追加到独立输入缓冲区；找到 `\r\n\r\n` 后解析请求行、请求头和 URL；将任务放入线程池；工作线程做路径检查、文件查找、MIME 判断和响应构造；通过写缓冲发送，部分 send 后保留偏移并监听 EPOLLOUT。

### 半包、粘包和 keep-alive

TCP 是字节流，不保证一次 send 对应一次 recv。每个连接保存独立输入缓冲区；未找到完整头部就继续接收；有 Content-Length 时判断请求体是否收全；解析完一条只消费已处理字节，剩余字节继续解析。keep-alive 需要保存读写缓冲、解析状态、请求数和最后活动时间；响应发送完重新监听 EPOLLIN，超时或协议错误时关闭。若当前实现是短连接，要明确说这是简化版本。

### 线程池如何保证安全？

线程池由工作线程、任务队列、互斥锁、条件变量和停止标志组成。提交任务时加锁入队并通知；工作线程等待“队列非空或停止”，取出任务后解锁再执行；析构时设置停止标志、广播并 join。队列必须有上限，满时拒绝、阻塞或返回 503，不能无限堆积。

### LRU、DJB2、双向链表和哈希表

静态资源缓存可以用哈希表按 URL 快速定位节点，用双向链表维护访问顺序：命中后移到表头，容量不足从表尾淘汰。DJB2 可用于 URL 或文件名哈希，再配合冲突处理定位缓存项。面试时还要说清缓存对象、容量、文件修改后的失效策略及并发锁；如果没有完整接入主流程，就说“完成模块和实验验证，主链路集成测试待补”。

### 路径安全、大文件和测试

限制请求行/请求头/请求体大小，拒绝 `..` 等非法路径；规范化绝对路径后检查其仍在 web 根目录内，并确认是普通文件。大文件采用固定缓冲区或 mmap/sendfile 分段传输，send 部分写出时保留偏移。用 curl 覆盖首页、图片、视频、404、非法路径和大文件，再用 wrk/ab 测吞吐、P95 延迟、错误率、CPU、内存和队列长度。简历没有给出 QPS，必须使用真实压测数据或说明待补测。

## 四、项目三：Qt 与 OpenCV 的人脸识别系统（2026.07 - 2026.08）

**技术关键词：** Qt、OpenCV4、MySQL、多线程编程、图像预处理。

### 项目介绍和完整流程

这是一个集用户管理、人脸采集、模型训练和实时识别于一体的桌面系统。Qt 负责可视化交互，OpenCV4 负责图像处理，MySQL 负责用户数据管理；输入支持摄像头实时流和本地视频文件；多线程把 UI 与视觉计算分开，在纯 CPU 环境下完成实时检测和身份匹配。

注册时采集多张样本并做裁剪、灰度化、缩放等预处理，保存样本和用户索引；训练阶段生成或更新模型；实时阶段读取帧、做人脸检测、提取特征并与用户特征匹配，超过阈值才判定为已知身份。简历没有写具体识别模型名称，面试时要按实际使用的模型回答。

### 为什么多线程？

UI 线程只负责窗口和显示，摄像头读取、预处理、检测和识别放到 worker 线程；worker 通过 queued signal/slot 把结果传回 UI，避免界面卡顿。worker 不能直接操作 QWidget；跨线程传递 QImage/OpenCV Mat 时要处理底层缓冲区生命周期，必要时深拷贝。

### 两种输入源如何统一？

将摄像头和本地视频都抽象为“产生下一帧”的接口，后续统一进入预处理、检测和识别流水线。切换输入源时释放旧对象、清空过期帧、更新 UI；文件结束和摄像头断开都要发出明确状态。

### 处理速度跟不上、摄像头断开怎么办？

先测量采集、预处理、检测、识别和显示耗时，再降低分辨率/检测频率、限制队列长度、只保留最新帧、跳帧或复用缓冲区。摄像头读取失败时释放设备、发出错误信号并退避重连，不能死循环占满 CPU。优化要同时观察帧率、延迟、误识别和漏识别。

### MySQL 和识别质量

数据库可保存用户 ID、姓名、样本或特征路径、创建时间等元数据；实时识别线程不应被数据库 IO 阻塞。光照、姿态和遮挡会影响识别，需要多角度采样、适当预处理、阈值验证和连续多帧确认。样本数量、CPU 帧率、准确率和表结构要按实际项目补充。

## 五、项目四：基于 STM32 的智能风扇系统（2026.04 - 2026.05）

**技术关键词：** STM32、HAL 库、DHT11、人体红外、红外遥控、PWM、OLED。

### 项目介绍

系统以 STM32 为主控，连接 DHT11 温湿度传感器、人体红外检测模块、PWM 电机驱动、红外遥控和 OLED。自动模式根据温度及人体是否存在自适应调节档位；手动模式通过遥控器控制启停和风速；OLED 显示温度、风速与工作状态。

我基于 HAL 库完成 DHT11 采集、人体红外检测、直流电机 PWM 调速、红外遥控解码和显示联动，并使用定时器中断、外部中断和任务调度改善响应。回答时要区分自己编写的驱动、参考 HAL 示例和实际联调部分。

### DHT11、红外和 PWM

DHT11 读取流程是主机拉低并释放数据线，等待响应，再按脉宽读取 40 位数据：湿度整数/小数、温度整数/小数和校验和。每一步要有超时；校验失败保留上一次有效值并设置故障标志。红外接收可用外部中断记录边沿、定时器测脉宽，再按实际协议解析引导码、地址码、命令码和重复码。PWM 由硬件定时器输出，占空比负责调节电机速度。

### 自动/手动状态机

建议显式管理 AUTO、MANUAL 和故障/关闭状态。自动模式先按需求确定人体检测和温度阈值的优先级，再映射风速；手动模式解析遥控键值更新启停和档位；任何时刻只允许状态机统一写 PWM。按键使用定时采样和软件消抖，OLED 降频刷新，不能阻塞传感器时序和控制任务。

### 异常处理

传感器读取失败时保留上次有效值或进入安全档位；遥控超时不应持续误触发；电机堵转、过流和系统看门狗要按硬件条件补充。面试需要准备实际 PWM 频率、自动模式阈值、遥控协议和显示刷新周期。

## 六、C/C++、Linux 高频基础题

- **`malloc/free` 与 `new/delete`：** 前者只分配和释放原始内存；后者还负责构造和析构，必须配对，数组使用 `new[]/delete[]`。
- **`vector` 与 `list`：** vector 连续存储、随机访问快、缓存友好；list 已知迭代器位置插入删除为 O(1)，但节点分散且有额外指针开销。没有明确需求通常优先 vector。
- **mutex、条件变量、信号量：** mutex 保护临界区；条件变量等待条件；信号量表示资源数量。固定加锁顺序、缩小临界区并用 RAII 降低死锁风险。
- **进程、线程和 IPC：** 进程地址空间独立、隔离好；线程共享地址空间、切换成本低但需要同步。IPC 有 pipe、FIFO、共享内存、消息队列和 socket。
- **GDB 与内存工具：** 用 `bt`、`frame`、`info locals` 定位崩溃；ASan 查越界和 use-after-free，LeakSanitizer/Valgrind 查泄漏。
- **网络字节序和 TCP：** 网络序为大端，使用 `htons/ntohs/htonl/ntohl`；TCP 是可靠字节流，应用层必须自行处理消息边界。
